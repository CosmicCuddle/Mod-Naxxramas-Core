## (a) Stage 8 and the two TBC-race settings

### What stage 8 means

**VERIFIED:** `PROGRESSION_PRE_TBC = 8`, comment `Karazhan, Gruul's Lair, Magtheridon's Lair`. The enumerator comment style on earlier values names content that becomes available at that value (`PROGRESSION_ONYXIA = 2` is commented `BWL available`). WotLK content is commented on `PROGRESSION_TBC_TIER_5 = 13`. [`IndividualProgression.h` L224–L244](https://github.com/Grimfeather/mod-individual-progression/blob/dd96f2b77e3ebfa2a4726bf785525ba133f1ab61/src/IndividualProgression.h#L224-L244).

**VERIFIED:** `hasPassedProgression(player, PROGRESSION_PRE_TBC)` is the comparison `GetPlayerProgressionFromQuests(player) >= 8`, after the gates below. A character with stored stage 0–7 fails it. A character with stored stage 8 through 18 passes it. Stage 13 therefore passes the same TBC boundary as stage 8. [`IndividualProgression.cpp` L31–L39](https://github.com/Grimfeather/mod-individual-progression/blob/dd96f2b77e3ebfa2a4726bf785525ba133f1ab61/src/IndividualProgression.cpp#L31-L39).

**VERIFIED:** there is no `PROGRESSION_TBC_TIER_3` enumerator. The line is commented out, so the enum jumps from 10 to 12. Quest id `66011` is still inserted by the module SQL, and the C++ loops are numeric, so value 11 can still be stored. [`IndividualProgression.h` L236–L237](https://github.com/Grimfeather/mod-individual-progression/blob/dd96f2b77e3ebfa2a4726bf785525ba133f1ab61/src/IndividualProgression.h#L236-L237), [`player_progression.sql` L25](https://github.com/Grimfeather/mod-individual-progression/blob/dd96f2b77e3ebfa2a4726bf785525ba133f1ab61/data/sql/world/base/player_progression.sql#L25).

### Where the stage is stored

**VERIFIED:** the header states that progression is derived from rewarded hidden quests `66000 + progression`. [`IndividualProgression.h` L418–L419](https://github.com/Grimfeather/mod-individual-progression/blob/dd96f2b77e3ebfa2a4726bf785525ba133f1ab61/src/IndividualProgression.h#L418-L419).

**VERIFIED:** `GetPlayerProgressionFromQuests` returns 0 when `player` is null or `!player->IsInWorld()`. Otherwise it scans `i` from `PROGRESSION_MOLTEN_CORE` (1) through `PROGRESSION_WOTLK_TIER_5` (18), quest id `66000 + i`, and keeps the highest `i` whose `GetQuestStatus` is `QUEST_STATUS_REWARDED`. It does not require a contiguous prefix. There is no player-setting field and no cached `uint8` on the player object in this class. A search of `src/*.cpp` and `src/*.h` at this pin finds no `PlayerSetting` / `UpdatePlayerSetting` use. [`IndividualProgression.cpp` L16–L28](https://github.com/Grimfeather/mod-individual-progression/blob/dd96f2b77e3ebfa2a4726bf785525ba133f1ab61/src/IndividualProgression.cpp#L16-L28).

**VERIFIED:** before the quest compare, `hasPassedProgression` returns false when IP is disabled, when `state` is 0, when the player is missing or not in the world, or when `progressionLimit` is non-zero and `state > progressionLimit`. `GetPlayerProgressionFromQuests` applies none of those gates. [`individualProgression.conf.dist` L286–L295](https://github.com/Grimfeather/mod-individual-progression/blob/dd96f2b77e3ebfa2a4726bf785525ba133f1ab61/conf/individualProgression.conf.dist#L286-L295), [`IndividualProgression.cpp` L1063](https://github.com/Grimfeather/mod-individual-progression/blob/dd96f2b77e3ebfa2a4726bf785525ba133f1ab61/src/IndividualProgression.cpp#L1063), [L1079](https://github.com/Grimfeather/mod-individual-progression/blob/dd96f2b77e3ebfa2a4726bf785525ba133f1ab61/src/IndividualProgression.cpp#L1079).

- The module must repeat team, RBAC, GM visibility, level, class, client race mask, zone, name, guild, free-text, and the `matchCount` / `displaycount` / `put(0)` / `put(4)` layout. Any later core change to `HandleWhoOpcode` will not be picked up.
- Returning false without a replacement send produces no `SMSG_WHO`.
- The boolean hook stops at the first script that returns false. Another module's `CanPacketReceive` can swallow `CMSG_WHO` first, or this module can hide it from a later script.
- Enabling the hook puts the script on every logged-in receive of every opcode, not only `CMSG_WHO`. `ServerScript`'s constructor enables every server hook when the enabled-hook list is empty. [`ServerScript.cpp` L72–L80](https://github.com/Grimfeather/azerothcore-wotlk/blob/8daffdabe9202c228e45d833c9a1d399597a15cd/src/server/game/Scripting/ScriptDefines/ServerScript.cpp#L72-L80).
- `sWhoListCacheMgr->GetWhoList()` is a public const accessor, so the rebuild can read the same cache. [`WhoListCacheMgr.h` L90](https://github.com/Grimfeather/azerothcore-wotlk/blob/8daffdabe9202c228e45d833c9a1d399597a15cd/src/server/game/Cache/WhoListCacheMgr.h#L90).

**POTENTIAL ISSUE, `CanPacketSend` on `SMSG_WHO`:** the packet is already built, including both counts. The reference is const, so the hook cannot `put` new counts into the object the core is sending. Returning false drops the entire packet. A module that copies the bytes, parses variable-length names, and sends a second packet still has to keep the two counts equal to the rows it kept. `OnPacketSent` has already observed the unfiltered packet, and a null socket never reaches `CanPacketSend`.

**VERIFIED:** Playerbots `WhoAction::Execute` answers a bot whisper with spec, skill, or trade text. The file contains no `CMSG_WHO`, `SMSG_WHO`, or `HandleWhoOpcode`. That action is not the client `/who` list. [`WhoAction.cpp` L26–L71](https://github.com/mod-playerbots/mod-playerbots/blob/d750b4b3a50effdf22bedc8032f0e8e5f7cb8091/src/Ai/Base/Actions/WhoAction.cpp#L26-L71). **UNKNOWN:** whether some other Playerbots file sends `CMSG_WHO`. This audit did not read the whole Playerbots tree for that string.

### Counts and query shape

- Vanilla-stage observer, empty `/who`: no Blood Elf and no Draenei row; `matchCount` and the displayed count both exclude them.
- Same observer, name field equal to an online Blood Elf's full name, and again as a substring of that name.
- Same observer, race mask with only bit 10, and again with only bit 11.
- Same observer, class mask, zone id, guild substring, and a free-text string that matches only a hidden character's zone or guild.
- More than `MaxWhoListReturns` legal rows, some of them Blood Elf or Draenei: hidden rows do not increase `matchCount` and do not take a displayed slot. The client total stays equal to the rows that passed the non-race filters plus the new predicate.
- Stage 8 observer and stage 13 observer: same faction Blood Elf and Draenei remain subject only to the existing team, security, visibility, level, class, mask, zone, and name filters.
- Opposite-faction hidden race, with and without `RBAC_PERM_TWO_SIDE_WHO_LIST`. The team check stays in front of any race predicate.
- A row with GM server-side visibility above `SEC_PLAYER`, including a hidden race, still obeys `GM.InWhoList.Level` and `RBAC_PERM_WHO_SEE_ALL_SEC_LEVELS`. The observer's own GM-invisible row still passes that one check.
- Feature switched off in the future module: the packet matches today's `HandleWhoOpcode` bytes, including both counts.
- Cache boundary: a Blood Elf who logs in, and a character who changes zone, can be absent or stale for up to the 5 second who-cache interval for every observer. A stage change of the observer is not stored in the cache; a live quest read sees it on the next `CMSG_WHO`.

### Stage, bots, and self

- New normal-account Blood Elf and Draenei with default `tbcRacesStartingProgression = 0` and no rewarded `66001`–`66018`: reader returns 0 after the successful login path. They are Vanilla-stage observers under `hasPassedProgression(PRE_TBC)`.
- Same races with `tbcRacesStartingProgression = 8`: login raises them to stage 8. They then pass the TBC boundary. This is config, not a hard-coded exception.
- Normal character completing Into the Breach while online: stored stage becomes 8 without relog when `disableDefaultProgression` is false, and the next `/who` from that character uses stage 8 if the reader runs inside the handler.
- Account matching `^RNDBOT.*`, level 60, after login: `ForceUpdate` to stage 0. Level 70: `ForceUpdate` to stage 8. Level 80: stage 13. A later level-up without login does not rewrite the stage.
- Same random bot grouped to a normal leader: stage becomes the leader's quest stage while online, including a downward rewrite.
- Altbot on a player account that does not match the bot or excluded regex: login uses the normal quest path, not the level rewrite. Their `/who` target row is still included whenever they are in `ObjectAccessor::GetPlayers()`.
- Quest template `66008` missing from the loaded `quest_template` cache: a rewarded `66008` reads as stage 0 through `GetQuestStatus`.
- Vanilla-stage Blood Elf observer, `/who` with their own exact name, and again with an empty mask that still has bit 10 set: expected result is unspecified until the owner chooses. Do not treat the world self-see rule as a `/who` result.
