# F15 Part29 — bounded offline report storage and lock acquisition

**ISOLATED DRAFT — DO NOT MERGE, DEPLOY, EXECUTE AGAINST SERVERS OR APPLY TO /root.** This patch is stacked on unchanged S4c DRAFT #141, and does not enable any monitor. Both Worldserver and Authserver remain **NOT OPERATIONAL** for F15.

## Change and safety contract

- Previously S2/S4c report publishing could emit an unlimited new finalized file and scan an ever-growing directory each time; blocking `flock(LOCK_EX)` could hang if another writer never released its lock. This child adds **pre-write backpressure**, not retention or a cleanup agent.
- A single shared exclusive lock protects quota decisions for both synthetic crash and warning/error publishers. The default limits are **256 reports total**, **128 of each kind**, **64 of each kind per daemon**, and **2 MiB of finalized crash/error report bytes**. Thus synthetic warning floods cannot consume the reserved crash lane, nor can Worldserver flood Authserver's per-kind allotment.
- At capacity a new unique report fails visibly with `OverflowError`. Existing finalized reports are never deleted, overwritten or silently evicted. Duplicate publication still returns `False` when the original is valid. The scanner counts even malformed files with a recognized finalized-report-shaped name conservatively, preventing invalid files from being ignored for capacity accounting. Quotas are not a disk-wide filesystem quota; unrelated files, indexes, restart sidecars and stale temporaries need separately reviewed bounds.
- Shared lock uses `LOCK_EX|LOCK_NB`, a monotonic **5-second maximum wait** and short sleeps; it raises `TimeoutError` without creating a report when unavailable. Safety checks now also verify lock-file owner UID. No external process is stopped or signaled.
- This is a **no-deletion** stopgap: on a full store, diagnostics cannot be published until a later owner-approved retention/archive design. No silent rotation can discard evidence. Additional events should be counted in a separate, authenticated overflow channel in an eventual approved design.
- The scan is now bounded *for new stores governed by these limits*, but legacy over-capacity directories can still incur scans on explicitly requested index rebuilds or duplicate attempts. There is no migration or cleanup of old data. Rebuilding history and publication are still O(N) in the number of existing named files; these caps keep N finite for a newly initialized store.
- Unkeyed SHA-256 remains **integrity only**, not provenance. Synthetic `verified` booleans do not bind service/identity. The owner-required R0 private launcher/permission facts, authenticated event source, least-privilege broker, format unification (#171 versus text), failover/retention policy and real fault-injected staging all remain unsolved.

## Part29 follow-up — directory-name scan budget (independent CS01 child)

**Still isolated offline research, NOT a production monitor or an operational fix.** Root cause of the further limit: the earlier count/bytes quotas bound *new finalized reports*, but existing legacy files, unrelated names, auxiliary index/sidecar files, and abandoned temporary names could be arbitrarily numerous. Under the old publisher, `os.listdir(self._fd)` materialized the entire directory before deciding whether the quota was full; both crash and warning/error rebuilds and S3 restart projections could repeatedly scan that large list. A same-UID actor or pre-existing overfull store can therefore defeat the intended bound on memory/CPU used per offline operation, even if no further report is admitted.

An isolated child now introduces `MAX_DIRECTORY_SCAN_ENTRIES = 4096` (**hard coded offline safety threshold, not approved operational retention**). `IncidentStore._dir_names_bounded()` calls `os.scandir(self._fd)` lazily against the already-pinned directory descriptor and refuses at **entry number 4097**, before allocating a potentially unbounded name list. All previous directory-name enumerate calls in `offline_store.py`, inherited `offline_restart.py`, and `offline_error_reports.py` (including abandoned-temp reaper, S3 sidecars, error history, crash history and quota) use this one method. The lock is held by supported callers; scanner safety does NOT establish authenticated user/process identity.

**Fail-closed policy:** when total directory entries exceed the threshold, publishing and/or rebuilding raises `OverflowError`; no immutable report, history index, sidecar or unrelated entry is removed/rewritten by the refusing scan. Existing process-local `capacity` rejection counter may increment; this is not an authenticated overflow log. Existing files remain in place; future owner-approved retention/migration and monitoring backpressure must be designed separately. The scan threshold counts *everything*, including the lock, index files, unfinished temporary files, sidecars and unrelated filenames. This is deliberately conservative, and older valid directories above the threshold will be unavailable for new writes until an owner-approved external repair strategy exists. Index histories are still derived from valid final reports; no attempt to correct or delete hostile files is made.

New synthetic tests verify: crowded directory refuses crash/error publication without deleting unrelated files, report/history bytes survive crowded rebuild refusal and recover after threshold is restored in the throwaway fixture, S3 sidecar scanning also refuses on excessive names, abandoned temp reaper refuses before removal at excess, and a fake 100,000-name scandir iterator is stopped after just `limit + 1` names. The original 11 bounded/quota tests and 135 inherited offline contracts remain mandatory.

**Residual issues not closed:** same-UID lock-file replacement / alternate flock inode domain, directory inode replacement by a permitted account after open, spoofable human-supplied process identity and boolean verification, unkeyed report hashes, remaining actual disk occupancy/index sidecar/temp byte count, service privilege/root policy, mixed text-versus-JSON canonical schema, and lack of an owner-approved authentic Worldserver/Authserver supervisor or staging. A scan budget is NOT a kernel filesystem quota, durable alert channel, evidence of a verified crash, nor a promise that every possible syscall is bounded under a hostile operating system. The cutoff intentionally trades availability for fail-closed behavior.
