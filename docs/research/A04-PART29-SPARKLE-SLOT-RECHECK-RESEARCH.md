At the immutable **public** Grimfeather AzerothCore `8daffdabe9202c228e45d833c9a1d399597a15cd`:

The same check participates in whether the client receives a **lootable corpse indicator**. It does **not** assert an individual quest item's current final eligibility.
2. `Loot::hasItemFor` in `LootMgr.cpp:906–949` consults the **already assembled** viewer-specific `PlayerQuestItems` entries and their `is_looted` flags without freshly calling `Player::HasQuestForItem` or rechecking inventory. This is a cached-row existence test, not a proof that the row will be lootable when the window is serialized.
3. `LootView::operator<<` in `LootMgr.cpp:1099–1164` independently calls `HasQuestForItem(itemid, 0, false, &showInLoot)` per viewer. An existing cached quest row for which the objective no longer needs that item can be sent as **`LOOT_SLOT_TYPE_LOCKED`** while the corpse-level check just found a cached row. This can explain a *possible* sparkle followed by an uncollectable displayed row without establishing any invalid server refusal or module involvement.
4. In `PlayerQuest.cpp:2338–2387` the **quest objective counter** (`q_status.ItemCount`) and **inventory count** (`GetItemCount(itemid, true)`) have different roles. If the stored objective counter is still short but the inventory already holds enough, `HasQuestForItem(...,&showInLoot)` can set `showInLoot=false`. Then `LootView` sets the **viewer-specific** `QuestItem::is_looted` flag, and if `!item.freeforall` also sets the **shared** underlying `LootItem::is_looted` flag. This is a source-backed side effect *during loot-window serialization* worth future scrutiny, not proof of actual player loss or a valid fix. It does not say the owner’s reported friend had mismatched counter/inventory.
5. `Player::StoreLootItem` in `Player.cpp:13861–13962` re-resolves packet `uint8` slot via the **viewer-specific** quest list and does fresh `AllowedForPlayer`, blocked/roll-owner, and bag-space checks. The `qitem` branch has distinct blocked semantics; `LootHandler.cpp:33–120` has different source checks and error paths. A lootable sparkle, a LOCKED slot, a native RELEASE, `EQUIP_ERR_ALREADY_LOOTED`, inventory failure, or actual `StoreNewItem`/`OnPlayerLootItem` are **different events**. The screenshot alone cannot identify which occurred.

## Part29 follow-up: Two-human shared-item and remaining-loot-count invariant

Independent additional public-pin source comparison `LootMgr.cpp:656–705, 906–949, 1099–1164`, `LootMgr.h:~323–368`, `Player.cpp:13861–13962` and `LootHandler.cpp:~327–469` establishes a narrower **possible consistency defect**, separate from any claim about owner H1/H2:

1. `FillQuestLoot` creates a player-specific quest entry for each eligible in-range party member. For one **shared non-Free-for-All** item, its `is_counted` guard increments global `unlootedCount` **once**, even if two eligible viewers each have a quest-slot mapping. The initial `AllowedForPlayer` uses `HasQuestForItem` **without `showInLoot`**, so it does not require inventory shortage in the same manner as the later quest window's additional check.
2. When human A's quest objective counter says the item is still required but A's bag count already satisfies it, `LootView` sets `showInLoot=false`. It marks A's player-specific `qitem->is_looted` and (if shared non-FFA) the underlying `quest_items[index].is_looted = true`. **The branch has no corresponding `--unlootedCount`**.
3. Another still-eligible human B consults the *same* `LootItem::is_looted` in `Loot::hasItemFor`, window serialization, and `LootItemInSlot`/`StoreLootItem`. Thus A viewing first can hide the shared drop from B, **even when B's quest objective remains short**. This is a source-shaped order-dependent risk, not a verified Worldserver or owner's incident. The legitimate reference is that B viewing and actually looting first consumes the one shared copy with the normal count decrement.
4. `Loot::isLooted` is `gold == 0 && unlootedCount == 0`. The source-shaped A-mismatch case leaves `unlootedCount=1` while the shared item is flagged looted. On creature `DoLootRelease`, the still-nonzero count takes the **not fully looted** branch, clearing the owner's round-robin turn (if applicable) but **not restoring the flagged item**. This may leave loot bookkeeping inconsistent and further explains a potential corpse marker/denial. Other items/gold, respawn cleanup, owner-installed hooks and concurrent activity may affect actual lifetime; none were reproduced.
5. In contrast, if A has already **completed** the quest objective and the row is sent `LOOT_SLOT_TYPE_LOCKED`, that branch does **not** set underlying `is_looted`; B may still acquire their legitimate copy. FFA hides A's own row without globally setting the shared-item flag in this branch. This underscores why the native row classification and both players' current counter/bag state are decisive.
