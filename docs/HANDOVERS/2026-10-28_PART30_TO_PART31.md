## 5B. F13 spellcaster charge accounting vs same-map owned portal — exact pinned source review, NOT RUN

**New source-backed conditional difference, 28 October 2026 UTC.** Read-only comparison of the untouched F13 `#187 @ de6816a1e3f94f2e530fca093dd596c11903b8d3` with pinned `Grimfeather/azerothcore-wotlk@8daffdabe9202c228e45d833c9a1d399597a15cd`. No new gameplay code, native test, world SQL, owner build, or in-game observation in this review.

- Native `src/server/game/Entities/GameObject/GameObject.h`: `AddUse()` increments `m_usetimes`, `GetUseCount()` reads it. Native `GameObjectData.h::GetCharges()` returns `spellcaster.charges` for `GAMEOBJECT_TYPE_SPELLCASTER` (22); it returns zero for other types without a charge rule.
- Native `GameObject.cpp::Use` (after an accepted `CastSpell(...) == SPELL_CAST_OK`) increments `AddUse()` for a spellcaster. Its `GameObject::Update` `GO_READY` branch, when spawned and the template's `GetCharges()` is **positive**, tests `m_usetimes >= max_charges`, resets the count and marks `GO_JUST_DEACTIVATED`. The deactivation branch may delete summoned/owned objects. Thus stock use counting **can control charged portal lifetime**, not merely a diagnostic counter.
- F13's outside destination policy requires `row->target_mapId == 0`. Pinned `Player::TeleportTo` follows a **same-map / non-new-instance** branch when `GetMapId() == mapid && !newInstance`. That branch can return accepted `true` with *no old-map player removal*, even while actual ACK/arrival has not completed; delayed teleport is another accepted branch. However the method performs teleport-related aura removal before the branch and can affect summoned objects independently. **A same-map portal is NOT guaranteed to survive**, and no installed object row/charge value or source map has been verified.
- F13 #187 snapshots `clickerOwnsPortal` before calling `TeleportTo` and **always skips** post-return `go->AddUse()` when true, regardless of same-map vs cross-map. This safely avoids unsafe dereference when an owned GO was removed (including far map teardown or relevant aura removal). But if **the clicker owns the GO, an accepted same-map teleport leaves the GO live and the GO's effective template has `spellcaster.charges > 0`**, the skipped increment can delay the ordinary charge-limit deactivation. For `charges == 0`, the native counter still differs but no **charge-threshold** deactivation is established by this code alone. For other-owner/ownerless GOs F13 still counts accepted successful use; an accepted request is **not** verified physical arrival.
- No unconditional replacement has been proven safe. Moving `AddUse()` **before** `TeleportTo` could count a refused teleport. Dereferencing `go` unconditionally **after** `TeleportTo` reintroduces the removed-object hazard. Looking up/reacquiring a GO after teleport requires separately reviewed lifecycle, map/thread, GUID and return/failure semantics. **Do not patch #187, protected #160, native core or SQL on inference alone.**
