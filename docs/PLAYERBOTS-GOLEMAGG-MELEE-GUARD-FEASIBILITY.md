A separate generic movement path may still be considered by the engine.

**Finding:** The missing generic-movement filter is a concrete source gap. **Do not claim that it definitively caused the user-observed oscillation until exact action execution is observed.**

## 2. Why the first proposed module-only listener is presently BLOCKED

- The pinned [`Engine.h`](https://github.com/mod-playerbots/mod-playerbots/blob/037c01418b5d01506917a3db9b44fd56ac5f965c/src/Bot/Engine/Engine.h) exposes `ActionExecutionListener`, public `Engine::AddActionExecutionListener` and `Engine::removeActionExecutionListener`.
- However, pinned [`PlayerbotAI.h`](https://github.com/mod-playerbots/mod-playerbots/blob/037c01418b5d01506917a3db9b44fd56ac5f965c/src/Bot/PlayerbotAI.h) declares `Engine* currentEngine` and `Engine* engines[BOT_STATE_MAX]` as **protected**, with **no public `GetCurrentEngine()` declaration**. Public `GetState`, `ChangeStrategy`, `GetStrategy`, `GetAiObjectContext` and `DoSpecificAction` do **not** establish module-owned access to `Engine::AddActionExecutionListener`.
- The available [`AiObjectContext.h`](https://github.com/mod-playerbots/mod-playerbots/blob/037c01418b5d01506917a3db9b44fd56ac5f965c/src/Bot/Engine/AiObjectContext.h) exposes actions/strategies/values, not the backing engine or an independent add-listener API. Deriving from `PlayerbotAI` merely to access protected data is not a safe integration with the existing PlayerbotAI object.
- [`PlayerbotAI.cpp`](https://github.com/mod-playerbots/mod-playerbots/blob/037c01418b5d01506917a3db9b44fd56ac5f965c/src/Bot/PlayerbotAI.cpp) builds separate combat, non-combat and dead engines. Combat state transitions call `ReInitCurrentEngine()`; `SelectiveResetStrategies` and `ResetStrategies` rebuild strategy state. The bot AI destructor **deletes all engine objects**. Any future listener needs proof of which engine it is attached to, repeat registration, and correct lifetime across relog/AI recreation.
- Pinned [`Engine.cpp`](https://github.com/mod-playerbots/mod-playerbots/blob/037c01418b5d01506917a3db9b44fd56ac5f965c/src/Bot/Engine/Engine.cpp) deletes every still-registered listener when its `ActionExecutionListeners` is destroyed. Its `Remove` only unlinks: it does **not** delete. Engine-owned listener plus Naxx-owned `unique_ptr`, arbitrary engine pointer caching or duplicated attachment could cause double deletion, stale pointers or leaks.
- **Important behavioural trap:** `Engine::ListenAndExecute` uses `AllowExecution(...) ? action->Execute(event) : true`. A veto skips `Execute` **yet returns true as the action-executed result**, subject to subsequent `OverrideResult`. This can affect scheduling/relevance and may not behave like an ordinary failed action. It is not safe to advertise an unconditional veto as a harmless fix.
- Overriding PlayerbotAI strategy lists or sending repeated master movement commands via exposed public methods is **not** equivalent to a reliable per-action block and risks new tug-of-war/movement loops.

**Decision at this checkpoint:** **Do NOT register an ActionExecutionListener from Naxx Core**, cast around protected `Engine*`, inject into private layouts, take ownership of Playerbots Engine objects or alter upstream files. No module-only veto architecture has passed S1.

## 3. Additional verified module-only **read-only diagnostic** opportunity

**NEW pinned-source finding:** although the module cannot safely reach `Engine::AddActionExecutionListener`, it **can request recent engine action text through an existing public method without touching `Engine*`**:

- Pinned [`PlayerbotAI.h`](https://github.com/mod-playerbots/mod-playerbots/blob/037c01418b5d01506917a3db9b44fd56ac5f965c/src/Bot/PlayerbotAI.h) declares public `std::string const HandleRemoteCommand(std::string const command)` as well as public `IsAltBot()`, `IsMelee(Player*)` and `IsTank(Player*)`.
- Pinned [`PlayerbotAI.cpp`](https://github.com/mod-playerbots/mod-playerbots/blob/037c01418b5d01506917a3db9b44fd56ac5f965c/src/Bot/PlayerbotAI.cpp) explicitly handles **`HandleRemoteCommand("action")` by returning `currentEngine->GetLastAction()`**. `"state"`, `"target"` and `"position"` are additional read-only branches, but are not necessary for a first tracer.
- Pinned [`Engine.cpp`](https://github.com/mod-playerbots/mod-playerbots/blob/037c01418b5d01506917a3db9b44fd56ac5f965c/src/Bot/Engine/Engine.cpp) collects action attempts, multiplier refusals, executed and failed results in `lastAction` and **trims it to a bounded recent tail of around 512 characters**. The remote action output is **recent log text, not proof of the exact action responsible for a specific movement**, and is not a stable machine-readable event stream.
- Existing Naxx Core [`BotRaidConsumables.cpp`](https://github.com/CosmicCuddle/Mod-Naxxramas-Core/blob/main/src/Systems/BotRaidConsumables.cpp) demonstrates a module-owned `PlayerScript` with `PLAYERHOOK_ON_UPDATE` / `OnPlayerUpdate(Player*, uint32)`. The owner's earlier pinned [`PlayerScript.h`](https://github.com/mod-playerbots/azerothcore-wotlk/blob/b7f06a16ac7120b5abc2e8d3f96a94265a363224/src/server/game/Scripting/ScriptDefines/PlayerScript.h) also declares this hook. This is a **candidate read-only sampling surface**, not yet compiled/tested for a new Golemagg tracer or proven invoked for every specific Altbot in that encounter.
- A Naxx-only **sampled diagnostic** could, subject to source/build and explicit operator test approval, inspect non-tank melee **Altbots on Molten Core map 409**, Magma Splash stack/duration, bot distance and current target, Golemagg health and the **recent** action-log tail. Rate-limit and bound messages. No motion changes, strategy changes, Engine listener access, AI `DoSpecificAction`, master-command injection, SQL or database writes.
- Before implementing: pin the operator's actual server revision, determine how the update hook relates to Playerbots AI execution/tick ordering, confirm the read-only getter does not unexpectedly trigger expensive or side-effectful work in that build, design strict `Enabled = 0` default + short sampling window + per-bot cap, and verify safe cleanup on leave/reset/logout. Do **not** auto-enable diagnostic logging or run it across a 40-bot raid by default.

**S2 draft implementation:** `src/Systems/BotGolemaggActionAudit.cpp`, registered by `src/NaxxramasCore_loader.cpp` behind `NaxxramasCore.Playerbots.GolemaggActionAudit.Enabled = 0` in the distributed config. The new code observes only player-character melee DPS **Altbots** (not tanks or healers) on map 409, in combat, while the named Golemagg target is live. It polls the public `"action"` and `"target"` read-only branches **no more often than every 2.5 seconds**, records at most **24 distinct action-tail samples per bot** per continuous eligible encounter, and clears its in-memory state on logout/encounter exit. It reports real Magma Splash stacks/duration and boss range/HP. It does **not** install a listener, veto an action, modify movement, apply spells or write any database. Code is an **unmerged draft** and has **not passed an exact pinned C++ build or in-game trial**.

**Prepared two-key one-bot safety gate (NOT PR #30 head yet):** In addition to `Enabled = 0`, the distribution defaults `NaxxramasCore.Playerbots.GolemaggActionAudit.AllowedBotName = ""`. Even an explicitly enabled observer refuses sampling without **one exact named Altbot**, not `*`, `all`, a comma-separated roster, or a prefix. An approved Grau-only pilot would require `Enabled = 1` AND `AllowedBotName = "Grau"`, plus all live Altbot/role/map/boss checks. The single-bot case-insensitive matching policy is isolated in `src/Systems/GolemaggActionAuditAllowlist.h` for standalone C++ tests and source-contract checks; this preparatory branch is **NOT YET COMPILED ON EXACT PINNED HEAD**. Config changes need a separately approved Worldserver restart; do not hot-toggle during an encounter.

**Prepared per-Player state hardening:** The newer candidate removes the global module-owned `std::unordered_map<GUID, SampleState>`. Instead the read-only observer stores a `SampleState : DataMap::Base` in **that Player object's `CustomData`**, using the pinned core's public `GetDefault`/`Erase` API already exercised by Hunter Pet Autocast audit patterns. This prevents competing Map threads from writing to one shared sampler map and naturally ties state to that Player's lifetime, with explicit cleanup on logout/combat exit/map exit/ineligible role. Temporary Golemagg target-lookup loss does **not** clear the cap. This design is source-reviewed but **not yet validated by exact-head pinned C++ or in-game tests**; the originally running full-link job remains on the earlier PR head.

**New S1 pinned threat-lookup finding (prepared separately):** `FindTargetValue::Calculate` in [pinned Playerbots `TargetValue.cpp`](https://github.com/mod-playerbots/mod-playerbots/blob/037c01418b5d01506917a3db9b44fd56ac5f965c/src/Ai/Base/Value/TargetValue.cpp) requires the bot to have a group and iterates only `bot->GetThreatMgr().GetThreatenedByMeList()` for a name match. Its own [`MCTriggers.cpp`](https://github.com/mod-playerbots/mod-playerbots/blob/037c01418b5d01506917a3db9b44fd56ac5f965c/src/Ai/Raid/MC/MCTriggers.cpp) uses the identical `find target / golemagg the incinerator` qualifier. Thus a missing returned boss does NOT necessarily mean Golemagg is dead or absent; it can merely be missing from that particular Altbot's threat list — exactly when action tracing could be useful.

**Separately prepared S2 adjustment, NOT yet on PR #30:** A per-Player `sawGolemaggInThisCombat` flag is set only after observing a living same-map Golemagg through that public lookup. If the lookup then disappears while the same Altbot remains in the eligible combat window, the read-only bounded `HandleRemoteCommand("action")` tail can still be observed. Logs include `boss_lookup_present=false` and unknown values `boss_hp_pct=-1`, `boss_distance_yards=-1`; **never infer boss HP or range from stale pointers**. If no valid boss was previously observed, no logging occurs. A real dead/wrong-map boss still terminates the sample state. This still proves neither the cause of movement nor that Altbot PlayerScript updates run on the operator fork. The code/tests have **no new exact-head pinned build evidence yet**.

**S3 source-contract tests:** `tests/test_golemagg_action_audit.py` and `.github/workflows/golemagg-action-audit-readonly.yml` cover explicit default-OFF, hook registration, Altbot/DPS/map scope, no mutating API calls, rate caps, and limitation wording. A green Python test is **not a C++ compilation result or server gameplay verification**.

**Important decision:** The draft tracer is a **potential Naxx-only investigation tool**, **not** a fix for Golemagg movement and **not** evidence that a safe module-only action veto is available. Owner approval, a matching-worldserver pinned full build, and a strictly controlled test with backup/restart/rollback are mandatory before enabling even this diagnostic.
