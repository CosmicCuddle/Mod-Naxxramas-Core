# NT1 Alt Bot Equipment Preservation — Grimfeather Source Decision (14 Oct 2026)

**Scope:** source investigation and unreleased fail-closed C++ guard for draft [PR #18](https://github.com/CosmicCuddle/Mod-Naxxramas-Core/pull/18). **No production code change, no server deployment, no approval to run `Apply` on real characters.** This follows the owner's express decision that Alt Bot NT1 must change talents **without any equipment mutation**. Random Bot behavior must be retained. **Owner's binding architecture decision, 14 October 2026: all implementation changes MUST stay inside `mod-naxxramas-core`; never modify AzerothCore, Playerbots, Individual Progression or ALE source, even via a separate compatibility patch.**

## Verified exact sources

Compared the existing draft importer to the owner's reported compatible AzerothCore fork at `Grimfeather/azerothcore-wotlk@a66f1bede6f5d905d9ab815715b4e2ee1c1f48e7`, to the pinned `mod-playerbots/azerothcore-wotlk@b7f06a16ac7120b5abc2e8d3f96a94265a363224`, and to `mod-playerbots/mod-playerbots@037c01418b5d01506917a3db9b44fd56ac5f965c`. These are *source review checkpoints*, **not** evidence of the running binary's exact sources.

### What is and is not causing the current block

1. In `src/Systems/BotTalentImport.cpp::ApplyValidated`, the actual **different-build** code invokes `bot->resetTalents(true)` and potentially invokes it **again** for best-effort rollback. It does **not** call `PlayerbotFactory::AutoGear`, `InitEquipment` or `Refresh`.
2. Playerbots' `PlayerbotFactory::Randomize` **does** combine talent selection and `InitEquipment` for bot generation. `PlayerbotFactory::Refresh` currently has the `InitEquipment` call commented out. This distinction is important, but neither fact eliminates the core reset risk. Do **not** disable Random Bot factory gear routines to fix an Alt Bot NT1 operation.
3. Grimfeather `Player.cpp::resetTalents` calls `sScriptMgr->OnPlayerTalentsReset`, may dismiss a pet, clears Titan's Grip/Dual Wield capability, and **unconditionally reaches `AutoUnequipOffhandIfNeed()`** on the nonempty reset path. Even a zero-point reset invokes the reset hook.
4. `AutoUnequipOffhandIfNeed()` **directly** calls `RemoveItem` + `StoreItem`, or `MoveItemFromInventory` and mails the item if bag storage fails. The body contains no `OnPlayerCanUnequipItem` precheck to let a module cancel this automatic move. The publicly available `OnPlayerUnequip` hook returns `void` and cannot veto the change.
5. The public `Player::_removeTalent` and `_removeTalentAurasAndSpells` methods are **not** a drop-in replacement for `resetTalents`. In the reviewed core, `_removeTalent` changes the map but does **not** decrement `m_usedTalentCount`; that counter is a protected implementation detail, and `InitTalentForLevel` uses it to recalculate free points. Calling these primitives from the module could corrupt accounting, miss hooks or bypass proper spell/action/auras cleanup. **Do not implement a partial reset by manipulating const-returned talent maps or using unsafe casts.**
6. Changing active specialization as a workaround does not help: `Player::ActivateSpec` calls `AutoUnequipOffhandIfNeed()`, handles glyphs/action bars and pets and is expressly out of scope.

**Conclusion:** Simply suppressing Playerbots gear refresh or removing the occupied-offhand guard is **not sufficient** to guarantee the owner's no-equipment-mutation rule. Neither of the inspected public core interfaces provides a demonstrably gear-inert, complete different-build talent reset. This is a **verified API/path limitation**, not proof that *all conceivable* module-only solutions are impossible.

## Module-only API alternatives reviewed

| Published core API | What it can do | Constraint for Alt Bot NT1 |
|---|---|---|
| `Player::resetTalents(true)` | Clear active spec and recalculate normal spent/free points | Calls `OnPlayerTalentsReset` and `AutoUnequipOffhandIfNeed()`; may unequip/mail offhand, violating the absolute equipment rule |
| `Player::LearnTalent(id, rank)` | Add/increase a legal rank with core prerequisites and point accounting | Cannot **remove** an old rank; by itself does not make a different fully spent 51-point build possible. Talent-spell/hook side effects and atomic failure handling still need proof before even considering an additive-only enhancement |
| `Player::_removeTalent` and `_removeTalentAurasAndSpells` | Update talent-map records and remove spell/aura effects | Do **not** provide a whole-reset transaction or correct protected `m_usedTalentCount` bookkeeping. Not an acceptable module-only full-respec substitute |
| `Player::ActivateSpec` | Change active spec and manage glyphs/action bars | Calls `AutoUnequipOffhandIfNeed()` and affects pets/actions; explicitly not a workaround |
| `OnPlayerCanUnequipItem` / `OnPlayerUnequip` | Gate some ordinary equips or report an unequip | The core's automatic offhand path directly calls storage/removal functions; it does **not** consult a cancelable before-unequip hook on that route |
| `PlayerbotFactory::AutoGear` | Bot equipment generation/replacement | Not called by NT1 Apply. Skipping it has no effect on the direct core reset's offhand path |

**Feasibility result:** A complete replacement of an already-spent 51-point active-spec build (such as Arndor's requested Holy Priest rebuild) is **not currently demonstrated safe using the reviewed public module-accessible APIs**. An **add-only** operation might be possible in narrower situations with unspent points, but it is neither a full respec nor proven equipment/pet-safe or transaction-safe. Do not expose such a partial Apply under a full NT1 import command without separate design, precise messages, and failure safety proof. The owner's required full Alt Bot talent-only change remains a separate **unsolved** engineering problem under the nonnegotiable module-only restriction.

## Read-only differential diagnostic (new draft-only milestone)

`.naxxbot talents preview <bot> <NT1>` and `repairpreview` already perform a strict **active-spec read-only talent comparison**. In this draft, when a requested build is **DIFFERENT**, the same verified rank maps now calculate and report the count of **rank points to add** and **rank points to remove**, without executing any changes. For example, a requested five-rank talent instead of an existing four-rank one reports `+1, -0`; swapping two different fully spent five-point talents reports `+5, -5`.

- Only compute counts after valid DBC/rank mapping, spec masks, player/class/level, and spent/free-point consistency checks. Malformed/corrupt ranks remain **CANNOT VERIFY**, without a misleading plan.
- An addition-only count is **NOT** permission to learn ranks or an assertion that scripts/pet/gear side effects are safe. It simply shows which part of a future implementation would not require deleting a rank.
- Any **negative** rank delta necessarily requires decreasing/removing some existing active talent ranks. A fully spent build differing from another equally fully spent build necessarily requires removals; `LearnTalent` cannot by itself perform that replacement.
- When at least one rank must be removed, `preview` / `repairpreview` now say **EXISTING RANKS MUST BE REMOVED**; when the change is purely additive they say **ADDITIONS ONLY**. Both explicitly state that **Alt Bot Apply remains BLOCKED**. Unverifiable talent maps never claim a safe change type.
- Neither the validator, `CheckApplyReadiness`, nor `ApplyValidated` uses these displayed counts to bypass the current universal Alt Bot changed-build refusal.
- The draft retains the approved zero-equipment-mutation rule, existing Random Bot behaviour and unchanged upstream sources.
- CI checks include real extracted C++ comparator cases for exact, additions-only, reduction of an existing rank and a full-budget rank swap. These compile/run tests do not prove worldserver runtime mutation safety.

The harness deliberately makes the **first** readiness preflight incorrectly return READY for a **DIFFERENT** Alt Bot, then proves the **independent second guard** still blocks before `resetTalents`, `LearnValidated`, `SaveToDB`, database writes or `ImportScope`. Its fake core pessimistically **moves any equipped offhand whenever reset is called**. The Alt Bot test confirms the offhand remains equipped and no reset is reached; a separate changed-build Alt Bot with **no offhand** must still be rejected. The nine scenarios also cover blocked preflight, authorized exact-match no-op, read-only access mode, Random Bot normal success, Random Bot successful rollback, Random Bot failed rollback, and unexpected spec switch. This tests control flow and no-change decisions more strongly than matching source text.

**Limit:** mocked interfaces cannot prove real AzerothCore or Playerbots hooks, mail, item legality, Worldserver runtime, transactionality or delayed bot activity. The harness **does not change real characters or make full different-build Alt Bot respec possible.** Keep PR #18 draft and the different-build Alt Bot refusal enabled until a fully module-only method is source-proven and independently validated.

## Last published in-place talent API candidate — reviewed (14 October)

**`Player::addTalent(uint32 spellId, uint8 addSpecMask, uint8 oldTalentRank)` is publicly declared**, unlike the protected `m_usedTalentCount`. Its implementation in Grimfeather `Player.cpp` ~3000–3065 can replace an **existing rank of the SAME talent** (if passed the real old rank), update its auras/spells and adjust `m_usedTalentCount` by the rank difference. This explains why some down-rank or add-only operations might be possible without calling `resetTalents`.

**It is not a complete full-respec API:** it cannot remove a talent's **last rank** while also decrementing the protected used-points counter. `_removeTalent` on its own clears a map entry but does not debit that counter. `SetFreeTalentPoints` only changes the publicly visible free-point field, **not** `m_usedTalentCount`. `InitTalentForLevel` derives free points from that counter and can invoke the unsafe `resetTalents(true)` when overspent. Faking an `oldTalentRank`, using a dummy rank to alter the counter, casting away const from `GetTalentMap`, or tweaking bonus point counts would be **unapproved integrity bypasses**.

Also ruled out the pinned Playerbots public factory helpers: `PlayerbotFactory::InitTalentsBySpecNo`, `InitTalentsByParsedSpecLink`, and `InitTalentsTree` call the unsafe `bot->resetTalents(true)` when `reset` is true. With `reset=false`, they learn additional ranks or templates; they do not remove an unrelated, already allocated talent. `TalentSpec::ApplyTalents` likewise only invokes `bot->LearnTalent`.

**Result:** Even after inspecting the less obvious published APIs, no safe, public, module-callable operation has been found that removes **all** old ranks, reconciles real used/free point accounting, keeps spells and dependent effects consistent, and guarantees **zero equipment movement** in success and failure. Do not implement a narrower downgrading experiment as if it were a full Alt Bot NT1 respec. The existing double changed-build rejection stays in place. See [Grimfeather `Player.cpp`](https://github.com/Grimfeather/azerothcore-wotlk/blob/a66f1bede6f5d905d9ab815715b4e2ee1c1f48e7/src/server/game/Entities/Player/Player.cpp#L3000-L3065) and [pinned Playerbots factory](https://github.com/mod-playerbots/mod-playerbots/blob/037c01418b5d01506917a3db9b44fd56ac5f965c/src/Bot/Factory/PlayerbotFactory.cpp#L1707-L1895).

## Offline database swap — examined and REJECTED (14 October)

A suggested way to avoid `resetTalents(true)` is to change `character_talent` rows while a bot is offline and reload it. **Do not implement this shortcut for NT1.** It is not a demonstrated gear-inert or transaction-safe full respec:

1. [Grimfeather `PlayerStorage.cpp`](https://github.com/Grimfeather/azerothcore-wotlk/blob/a66f1bede6f5d905d9ab815715b4e2ee1c1f48e7/src/server/game/Entities/Player/PlayerStorage.cpp#L5545-L5590) loads saved spells/talents **before** inventory, then calls `InitTalentForLevel()` and `_LoadInventory()`. Talent effects can therefore influence whether existing gear is legal on login.
2. [`_LoadInventory`](https://github.com/Grimfeather/azerothcore-wotlk/blob/a66f1bede6f5d905d9ab815715b4e2ee1c1f48e7/src/server/game/Entities/Player/PlayerStorage.cpp#L5961-L6090) checks `CanEquipItem` for equipped items. On failure, it **removes the inventory row and sends the same item by mail**, violating the owner's prohibition against even temporary gear moves. Further invalid, unknown, expired or map-limited items may be deleted independently of the talent change.
3. [`Player::_LoadTalents`](https://github.com/Grimfeather/azerothcore-wotlk/blob/a66f1bede6f5d905d9ab815715b4e2ee1c1f48e7/src/server/game/Entities/Player/Player.cpp#L15450-L15465) reconstructs talents using `addTalent` and spell/aura activation, and `InitTalentForLevel` can itself call `resetTalents(true)` when point accounting is inconsistent. A hand-edited DB build cannot be assumed to match the live player state/abilities.
4. [Normal `SaveToDB`](https://github.com/Grimfeather/azerothcore-wotlk/blob/a66f1bede6f5d905d9ab815715b4e2ee1c1f48e7/src/server/game/Entities/Player/PlayerStorage.cpp#L7260-L7285) persists player talents/spells/inventory from the current in-memory character. Direct SQL while the bot is online can therefore be lost or conflict with subsequent saves. Force logout/relogin changes world/session state, is not a transparent talent import and remains subject to the login inventory behavior above.

**Decision:** Never attempt an unreviewed direct `character_talent`/`character_spell` SQL overwrite, fake reset spell, forced relog, item-guid temporary relocation or private data/member bypass as NT1's `Apply` path. Neither a source-level SQL transaction nor preserving item-instance GUIDs on disk proves that their original equipped slots survive login. A compatible **module-only, zero-item-change full respec remains unproven**. Preserve exact-match no-op and fail-closed changed-build guard.

## Narrow, safe progression

1. Preserve the **currently installed** read-only diagnostics and conservative offhand/pet block. In **draft PR #18 only**, `CheckApplyReadiness` now also refuses **all different/indeterminate Alt Bot builds** before any `ImportScope`, reset, talent learning, persistence or equipment action, even with an empty offhand and no active pet. A **second independent rejection in `ApplyValidated`**, after the authorized EXACT-build no-op and before `ImportScope`, also stops every nonrandom bot if that preflight is ever relaxed by mistake; the existing two-reset path can now be reached only by Random Bots. Authorized **EXACT** build no-op remains eligible; Random Playerbot reset/recovery remains unchanged. This is intentionally safer but stricter than the prior ordinary Alt Bot Apply path, and is **not** the desired completed talent-changing feature. Do not retest on Arndor or Rakari with `Apply`.
2. Keep PR #18's **exact-match no-op** isolated: after full authorization and legal-build/old-state checks, a provably identical active build can return without reset, learning, AI factory, equipment, mail, spec switch or persistence. That narrow candidate needs owner-approved disposable-bot validation; it does *not* perform a different-build change.
3. Continue examining published extension points for a truly module-owned **atomic, gear-inert** different-build operation. Any proposal must reconcile `m_usedTalentCount`, both talent/spell maps, prerequisite rank order, dependent auras and abilities, dual wield/Titan's Grip, pet preservation, rollback and delayed Playerbots actions.
4. **MODULE-ONLY STOP RULE:** Only use reviewed, already-available core/Playerbots interfaces from `mod-naxxramas-core`. Do not propose, draft, install, or require ANY AzerothCore, Playerbots, Individual Progression, or ALE source patch, including an optional core API/primitive. **If a safe module-only different-build implementation cannot be proven, keep different-build Apply blocked before mutation** and report the limitation plainly. Merely skipping `AutoUnequipOffhandIfNeed` would not establish safety or correct talent accounting.
5. Before enabling changed-build Apply, run compiled and isolated fault-injection tests using **disposable** Alt Bots and a tested restoration procedure: occupied focus/shield/weapon, staff/polearm, Titan's Grip/Dual Wield, no offhand, both specs, pets, full bags/mail, every class, failed talent learning, rollback failure, delayed AI maintenance, save/logout/restart. Confirm original item-instance GUIDs and slots (and absence of new mail or replacement items) on each path.
